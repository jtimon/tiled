* TilVm startup, text-command and shared-library integration

[[file:keybindings.org][Commands]] | [[file:../issues/open/5.org][Integration tracking]]

** Planned handoff to Til #370: host-supplied prelude

*** Goal and first slice

Let a compiled application supply its guest-facing API before loading user
configuration, so =~/.tiled/init.til= does not import a checkout-specific
=gen/tiled_startup_api= path. The host knows where its installed runtime and
bindings live; the user should only write ordinary Til configuration and
relative imports of their own helper modules.

Add an optional, per-VM/per-load host prelude to the public =std/tilvm= API.
The desired input is source text with a logical module name/origin and an
explicit base directory for relative imports/links. It can contain generated
=ext_func=/=ext_proc= declarations, required record/signature declarations,
=link(...)= directives and small Til wrappers. It may also import a packaged
binding module rather than embed all declarations. Do not hand-maintain a
second ABI description when generated bindings already provide it.

This is one entry-module load with an additional implicit dependency, not a
request for arbitrary incremental eval or a second successful =load_file= on
an already sealed VM. Preserve the existing load/lookup/callback lifecycle.
Choose the smallest public API spelling consistent with the SDK; the spelling
is not prescribed here and should be confirmed in the Til session before
introducing a new public surface.

*** Existing machinery to reuse

- =src/core/modes.til= defines GUI as
  =Mode(needs_main=true, auto_import="src/modes/gui", decls_only=false)=.
- =src/std/mode_type.til= supplies the =Mode= record; =auto_import= is a module
  path, not a special native-registration mechanism.
- =src/modes/gui.til= is an ordinary module containing imports, native links,
  declarations and helper functions.
- =src/self/loader.til=: =resolve_mode_import= creates an implicit dependency
  before typing; =load_import_unit= shares import deduplication and cycle
  handling. =load_mode_file= resolves auto-import paths relative to their
  defining mode file.
- Current public =TilVm.load_file= accepts one successful =mode lib= entry,
  passes an empty extra-modes list, and exposes no source/prelude loading API.
  The loader separately rejects embedded entry modes other than =lib=.

Use that import/program machinery for the host prelude rather than concatenate
text onto init or generate a temporary wrapper entry point. Merely opening a
native library is insufficient: the declarations must also be available during
name resolution and type checking.

*** Required semantics

- Prelude public declarations are available to init without a user-written API
  import. Specify the scope for imported user helpers too: they should be able
  to use the application API without repeated absolute imports. Do not globally
  redefine SDK/core =mode lib= or inject the application API into its own prelude.
- Keep original user filenames and line/column positions. Relative user imports
  remain relative to the importing user file; prelude imports/links resolve from
  the host-provided origin/base. Prelude failures identify the prelude itself.
- Treat the prelude as a named module with normal visibility and import identity
  rules. Define collisions explicitly; do not silently overwrite guest symbols.
  Reuse existing deduplication and cycle handling instead of a separate registry.
- Retain source/AST/code for the VM/callback lifetime; the host must be able to
  release its input Str after loading. Errors and results remain owned values.
- Failure must return structured diagnostics, leave retry semantics intact and
  not terminate the host. A failed candidate must not invalidate another VM's
  retained callbacks. Native side effects are still not universally rolled back.
- Loading and later invocation require no compiler executable, generated entry
  source or writes into the user's configuration directory.

*** Acceptance tests for the Til session

Build a separate ASAN host against an isolated installed SDK. It should create
the user config after host compilation, supply the API prelude and run with an
empty PATH and private HOME. Verify:

- init with no explicit API import can call a generated native binding and
  observe the same library-owned state as the compiled host;
- a relative user helper can use the intended prelude visibility;
- prelude and user errors have the correct origins and unchanged line numbers;
- relative imports/links, duplicate imports, collisions and missing dependencies
  have defined behavior;
- releasing the original prelude Str does not invalidate later guest callbacks;
- independent VMs, failed-load retry, candidate rejection and teardown preserve
  the existing ownership/error contracts;
- the existing no-prelude =load_file= API and its tests continue to work.

*** Tiled adoption and packaging

Once installed, Tiled will supply its generated binding/checked-wrapper prelude
and remove the absolute API import from the user example. Keep =~/.tiled/init.til=,
its zero-argument =init()= and relative helper imports. Add a real-executable
regression with no API import and no compiler on PATH before changing the loader.

The application package must still ship its matching runtime assets and native
library; hiding the import does not make a copied executable self-contained.
Ownership of those assets and discovery of their installed locations belongs
to Tiled's packaging work, not to user configuration or a Tiled-specific SDK
builtin. The current build-time paths remain until that work is implemented.

=mode config= is a possible later convenience using auto-imports and an explicit
entry-point/policy contract. It is not necessary for this first slice. Neither
a mode name nor a prelude alone establishes isolation from native code. Revisit
mode/script syntax and restrictions separately when their requirements are
clear; keep =mode lib= for the existing module-plus-init protocol for now.

** Current implementation

Tiled uses TilVm for startup configuration and live general/selected-text commands.
=src/guest_transform.til= applies checked guest results to editor state;
=src/guest_commands.til= retains and dispatches those typed handles without
coercing them to native function pointers. Standalone tilminal still uses its
compiled init loader.

** Interpreted startup

=lib/libtiled/tiled_startup.til= owns startup settings and built-in keymap
overrides in one shared library. Both the GUI executable and the interpreted
init import =gen/tiled_startup_api.til=, which names that same shared object.
=src/tiled_init.til= loads =~/.tiled/init.til= and calls its zero-argument
=init()= in-process. The host adopts the final snapshot, validates registered
guest commands and retains their VM throughout the GUI loop. Failed init or
registration clears partial handles/settings and stops startup. At shutdown,
the registry is destroyed before its VM.

The user API is =tiled_options()= / =tiled_configure(settings)= plus
=tiled_bind= / =tiled_unbind= for existing commands. Obtain settings from
=tiled_options()= rather than constructing a partially populated record.
The build generates =gen/tiled_init.til= with the binding's explicit path, ready
to copy into the config directory. See [[file:configuration.org][configuration and migration]].

=test/init_gui.til= runs the actual executable with config files created after
the build and an empty PATH. It checks imported settings, window/draft/session
values, bindings, init/GUI process identity, errors and version bypass.
=test/init_model.til= checks owned snapshots, error rollback and retry under ASAN.

#+begin_src sh
./make.til
til build --usize=64 --asan -o tmp/check_init_model -c tmp/check_init_model.c test/init_model.til
env PATH= ./tmp/check_init_model
xvfb-run -a -s "-screen 0 1600x1200x24" til run --usize=64 -o tmp/check_init_gui -c tmp/check_init_gui.c test/init_gui.til
#+end_src

** Live guest text commands

Keep the generated binding import from =gen/tiled_init.til= and add a public
guest procedure plus its registration:

#+begin_src til
bracket_region := proc(text: Str) returns Str {
    // The current callback contract is proc; keep a pure example effectful.
    noop_proc()
    return format("[", text, "]")
}

init := proc() {
    tiled_text_command("bracket-region", "bracket_region")
    tiled_bind("text", "C-k b", "bracket-region")
}
#+end_src

Select text, then use the binding or =M-x bracket-region=. Registration stores
the command name and exported guest symbol; lookup happens after init returns.
Imported helpers can define the symbol. Missing symbols or incompatible
signatures stop startup with diagnostics. Empty names and collisions with
built-in command names are rejected. Re-registering a guest name during
init replaces its earlier symbol; the last registration wins.

Each registered command retains one typed callback, including its captured
state, for repeated invocation. These are startup registrations: calling the
registration/configuration functions later does not reconfigure the running
editor. Zero-argument =tiled_command= callbacks can now use the
[[file:live-buffers.org][live buffer API]] without a selection; hot reload remains later work.

M-x lists guest commands with their effective bindings, marking them unavailable
without a nonempty text region or inside terminal/minibuffer contexts. Bound
invocations enforce the same restrictions without calling the guest. Successful
replacement clears the region and creates one undo step. Panic/exit failures
leave its text and region intact, show a status message and print full diagnostics;
the editor remains usable. Guest capture state or native side effects already
performed are not rolled back by either failure handling or editor undo.

The integration uses a separate typed registry, not captured =EditorAction=
closures, avoiding the native closure ownership problem documented below.

#+begin_src sh
./make.til
til build --usize=64 --asan -o tmp/check_guest_commands_model -c tmp/check_guest_commands_model.c test/guest_commands_model.til
env PATH= ./tmp/check_guest_commands_model
xvfb-run -a -s "-screen 0 1600x1200x24" til run --usize=64 -o tmp/check_guest_commands_gui -c tmp/check_guest_commands_gui.c test/guest_commands_gui.til
#+end_src

The model tests registration/replacement, partial-load cleanup, captures,
selection/context restrictions, discovery, undo and error recovery under ASAN.
The GUI test runs the real application with private HOME and empty PATH, invokes
commands by key and M-x after startup, checks Unicode file results and undo/redo,
survives guest panic/exit and verifies terminal isolation and rejected registrations.

** Text-transform adapter contract

- The host creates/owns a =TilVm= with its matching installed SDK root, loads
  one guest module, and calls =EditorGuestTransform.lookup(vm, name)=.
- The guest symbol must match =proc(Str) returns Str= exactly. Using a proc
  permits retained mutable capture state; a pure func signature is distinct.
- =transform.apply(editor)= acts on a nonempty region in the focused text
  buffer. Without a region, or in a terminal buffer, it returns false without
  calling the guest. Guest code receives a copied string, not editor pointers.
- A successful call replaces the region as one undo step, or joins the host's
  already-open command transaction. The result is copied into editor-owned text.
- A failed lookup/call throws =TilVmError=. The adapter does not alter editor
  text, selection, dirty state or undo history on call failure. Guest effects
  such as changes to its captures can remain; this is not VM rollback.
- Retain the typed adapter for repeated invocation. Destroy it before its VM.
  Returned editor text and owned diagnostics remain usable after teardown.

** One compiled library, native host and interpreted guests

TilVm now permits imports that link prebuilt native libraries through the
existing FFI bridge. The compiled host and guest can consume the same generated
Til binding; the guest does not need a separately reimplemented API or dynamic
host-function registration for those exported library calls.

=test/guest_shared.til= builds a tiny native text-store fixture and an ASAN host
using Tiled's actual editor/guest-transform code. Both the compiled host and
two guest VMs import its generated binding, rewritten to name the same explicit
=.so= path. The host creates the guest source only after compilation and runs
with private HOME and empty PATH.

#+begin_src sh
./make.til
til run --usize=64 -o tmp/check_guest_shared -c tmp/check_guest_shared.c test/guest_shared.til /usr/local/lib/til
#+end_src

The Linux test verifies:
- Native initialization and guest updates are visible to the compiled host.
- A second VM sees the same state, including changes made by native calls.
- Unicode strings cross both boundaries and become ordinary editor-owned text.
- A missing library returns a load error; the same VM can retry successfully.
- A native throws contract reaches the host as a structured guest-call error,
  leaving the rejected editor selection unchanged.
- Destroying one or both VMs does not reset/unload the library used by the
  host; returned strings remain valid after subsequent native changes.

For stateful APIs, both sides must use the same shared object. Statically
linking a library into the host while a VM loads its dynamic counterpart can
create two independent copies of its state. Regenerate bindings and rebuild
against matching compiler/target/USize/ASAN settings, as with libterminal.
Native libraries are process-lived; creating a fresh VM does not reset their
globals. Runtime =link_c= compilation is still rejected by TilVm.

The production [[file:live-buffers.org][live buffer API]] now reaches one native owner through a typed
shared-library dispatcher. The full model is not exported into the DLL yet;
the same editing/undo implementation remains in the host. Buffer API edits made
by one general command share an undo group, including completed edits before a
failure. Arbitrary native-library side effects are still not automatically undone.

** Findings for the next TilVm/compiler upgrade

These were observed while composing the prototype with native command slots
on Til =fcbe4e79a=. They are not failures of the direct typed guest-call path.
The shared-library probe above uses that typed path and does not depend on
capturing an adapter in a native command closure. These older findings have not
been reclassified as fixed merely because native library loading now works.

*** Owning adapter capture: missing generated clone

This closure shape failed C compilation with an implicit declaration of
=EditorGuestTransform_clone= in the generated closure-clone function:

#+begin_src til
make_command := proc(mut vm: TilVm) returns EditorAction {
    transform := EditorGuestTransform.lookup(vm, "transform")!
    return proc(mut editor: EditorState) [own mut transform] {
        transform.apply(editor)?
        catch (err: TilVmError) { println(err.to_str()) }
    }
}
#+end_src

The compiler should account for clone calls introduced by closure generation,
and the integration needs an explicit ownership contract for stored actions.

*** Bounds checking inside a throwing procedure

Indexing =editor.nodes[editor.focused]= and =editor.buffers[view.buffer]= inside
the throwing =apply= procedure generated bounds-failure expressions assigning
=_err_kind = 1= even though that function's hidden error argument is =I64 *=.
The C compiler rejected the integer-to-pointer assignment. Host selection
snapshotting now has its own non-throwing helper, separate from guest invocation.

*** Borrowed native command capture: dangling closure box

This local capture compiled, but invoking the registered action failed ASAN:

#+begin_src til
mut transform := EditorGuestTransform.lookup(vm, "transform")!
action := proc(mut editor: EditorState) [mut transform] {
    transform.apply(editor)?
    catch (err: TilVmError) { println(err.to_str()) }
}
commands.command("guest-transform", action)
commands.invoke("guest-transform", editor)
#+end_src

Generated registration assigned the callable pointer to the command field;
the caller then freed the closure box, and =EditorCommands.invoke= read it.
The registry/callable ownership boundary must retain the closure or reject
the escape, rather than depending on a local keep-alive call. The
GUI now resolves named keys and invokes separately retained typed guest handles.
Routing these through captured native EditorAction closures should still wait
for that ownership contract to be settled and regression-tested.

** Feedback to Til #370: installed d3ae8b3f1

This audit used installed Til, not the development binary. Both applications
built without source changes. The five ASAN embedding drivers
(=live_buffers_model=, =guest_commands_model=, =init_model=, =guest_transform=
and =guest_shared=) passed with empty compiler PATH during host execution.
Seven Xvfb drivers passed: =live_buffers_gui=, =guest_commands_gui=, =init_gui=,
=session_gui=, =clipboard_gui=, =keymap_gui= and =command_discovery_gui=.

The native-record provenance/string materialization fix is useful: native
fields must not retain VM literals or borrowed views after VM destruction,
even when layouts match. The SDK reload tests also exercise the right lifetime
sequence: validate a separate candidate, retain old callbacks on rejection,
then destroy old callbacks before their VM when publishing the replacement.

*** Remaining failures reproduced on this version

These are diagnostic probes of paths Tiled currently avoids, not failures of
the production integration tests above.

| Probe | Observed result |
|-------+-----------------|
| Owning an EditorGuestTransform capture in EditorAction | Generated closure clone calls missing =EditorGuestTransform_clone=; C compilation fails. |
| Borrow-capturing an adapter through EditorCommands.command | ASAN heap-use-after-free in =EditorCommands_invoke=; the closure box was freed after registration. |
| Explicit =callback.clone()= on an EditorAction parameter | Rejected with =no method 'clone' for type 'unknown'=. |
| Vector indexing inside a genuinely throwing function | C bounds failure still assigns =_err_kind = 1= to an =I64 *=. |
| Generated enum binding | Importing a two-case exported enum panics at =core/ast.til:41=, unwrap of None. |
| Typed native throw into a larger host | Library emits error ID 5; host compares against 6 and misses the catch. |
| Direct EditorState export plus existing model imports | Duplicate terminal/tab/undo/model declarations and invalid positional nested defaults remain. |

The owned/borrowed adapter shapes are shown above. In both probes the VM
outlived the command table; the borrowed adapter was explicitly destroyed only
after the table. We need a supported ownership contract for captured callables
stored in ordinary struct/Vec command tables. This may require a Tiled API
change; passing the runtime callable-slot corpus alone does not establish that
our registration pattern is sound. Keep the typed guest registry meanwhile.

Minimal indexing shape, including a real throw so the declaration is valid:

#+begin_src til
Problem := struct {}
indexing := func(values: Vec(I64)) returns I64 throws Problem {
    if values.len() == 0 { throw Problem() }
    return values[0].clone()
}
#+end_src

Minimal enum library: building succeeds, but translating a consumer of its
generated binding fails:

#+begin_src til
mode lib
ProbeOperation := enum { Read, Write }
probe_operation := func() returns ProbeOperation { return ProbeOperation.Read }
#+end_src

For the error-ID probe, a library function throws =NativeProbeError(code=7)=.
A host importing =std/tilvm= plus the generated binding creates/loads a VM,
then calls that function with =? catch (err: NativeProbeError)=. Generated
library code writes 5 into the hidden error-kind slot; generated host code tests
6, skipping the catch. Our live-buffer ABI therefore retains explicit reply
errors and raises typed errors in caller-local Til wrappers.

*** Priorities and design feedback

- Prioritize cross-library error ABI and generated-binding composition,
  including enums/nested defaults. They constrain moving the model into a DLL.
- Clarify/test captured callable retention in real command-table shapes;
  the recent mutable-slot fixes do not close this case.
- Application-supplied import roots/module resolution would let init use a
  stable Tiled import rather than a generated absolute binding path.
- Mutable native config references should be an option, not a reason to
  abandon snapshots/staging. Our cold-start loader resets shared settings and
  registrations; it is not a drop-in reload transaction. Reload must publish
  validated settings, bindings and callbacks together.
- Keep the distinction between callback replacement and native side effects.
  A candidate can edit a live buffer or write a file before failing. Tiled
  should stage configuration and restrict live-buffer writes during candidate
  initialization; TilVm should not claim universal rollback.
