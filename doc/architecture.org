* Application, desktop and layout model

[[file:../README.org][Tiled]] | [[file:progress.org][Progress]] | [[file:keybindings.org][Commands and keybindings]]

The editor now has separate buffers, views and a binary split-layout tree,
implemented in [[file:../src/editor_model.til][src/editor_model.til]]. It displays them inside one GUI window.
Desktop window management and multiple OS-level frames remain future work.

** Buffers, windows and frames

Use Emacs's distinction when discussing the editor:

- A buffer owns content, such as a document or scratch text, independently
  of where it is displayed.
- An editor window (also called a view) displays a buffer. Cursor and scroll
  state belong to that view, so several views can display the same buffer.
- A frame is an OS-level window containing editor windows and their layout.
- An external client is another application's window, such as Firefox,
  managed by Tiled's desktop host. Its lifecycle differs from an editor
  view; a shared layout model should preserve that distinction.
- A workspace groups a layout of views or external clients, depending on
  the host.

The current Emacs-style split bindings are:

| Binding | Result                         | Divider    |
|---------+--------------------------------+------------|
| C-x 2   | One view above the other       | Horizontal |
| C-x 3   | Views side by side             | Vertical   |
| C-x 0   | Close the current view         |            |
| C-x 1   | Keep only the current view     |            |
| C-x o   | Focus the next view            |            |

Splitting a view shows the same buffer in both views, initially copying the
cursor and scroll positions. Subsequent navigation is independent. Shared
edits update all views and adjust other views' cursor positions to track
the surrounding text. Closing a view does not discard its buffer.

Splits can be nested: only the focused view is divided. Closing it promotes
its sibling subtree, and closing the last view is refused. =C-x 1= preserves
the focused view and its buffer. Focus cycles in layout order with =C-x o=;
clicking a pane also focuses it. Each pane clips its own text and has a
mode line, with the focused pane highlighted. Layouts adapt to resizing.

Opening a file changes only the focused view's buffer. Opening an already
loaded file reuses its buffer, including unsaved edits. =C-x b= switches
buffers by name and =C-x C-b= lists them. Views remember cursor/scroll state
for previously displayed buffers. Shared edits adjust remembered points too.
Splits copy that history; focus and switching then evolve independently.

=C-x k= kills a buffer after confirmation if it is modified. All live views
and their histories stop referring to it before its storage can be reused.
Affected views select another buffer, with a fresh scratch buffer when the
last one is killed. Stable buffer slots keep other buffers' identities intact.
=C-x 5= is deferred until Tiled supports multiple OS-level frames.

[[file:../src/minibuffer.til][The minibuffer model]] handles prompt text, filtering, selection and completion.
[[file:../src/editor_buffers.til][Buffer commands]] supply candidates and interpret acceptance/confirmation.
The GUI draws the prompt and dispatches an ordered stream of key and text
events, so a prompt's opening key cannot become its first input character.

[[file:../src/editor_exit.til][Exit state]] snapshots the live modified buffers once per exit attempt.
Discarding advances that attempt without clearing a buffer's dirty flag, so
later cancellation preserves its unsaved state. Saving targets a buffer ID
without changing the focused pane. Window-close callbacks join the same
ordered queue as key/text events; typing received before a close request is
applied before the modified-buffer check.

Desktop placement and editor splitting can eventually share layout
operations without treating external windows as buffers.

** Hosting modes

- Application: an ordinary OS window under the user's existing desktop,
  containing Tiled's own views. This is where the current editor starts.
- Window manager: on X11, Tiled manages application windows on an existing
  display, handling placement, focus, workspaces and global shortcuts.
- Nested desktop: an X server such as Xephyr supplies an outer window;
  the same Tiled window manager runs inside it. External applications
  launched against that display appear inside the nested desktop.

Commands, configuration, keymaps and layout policy should be shared across
hosts. The launch interface for the future desktop hosts is still a design
question, not an implemented set of flags.

** What mode gui provides

Til's =mode gui= currently supplies raylib, tinyfiledialogs and helpers for
drawing, input and dialogs. It is useful for our own editor views and UI.
It does not supply a window manager or embed another application's window
inside a raylib pane.

Launching Firefox is a process operation. Firefox connects to a display;
that display's window manager controls its window. Containing Firefox in
an outer desktop window requires a nested display server/compositor, rather
than merely launching it from a raylib program. A separate Firefox instance
and profile may be needed when testing a different display.

X11 window management will need Xlib or XCB integration. Under Wayland,
Tiled would need to be a compositor, potentially using an existing
compositor library. Xephyr is a proposed first environment for developing
and testing an X11 host.
