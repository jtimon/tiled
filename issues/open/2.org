** OPEN #2 Show the til logo as a single glyph in tilminal's prompt

*** Transfer and migration context

Transferred from [[https://github.com/jtimon/til/blob/master/issues/cancelled/159.org][Til #159]], closed there as transferred. The
[[https://github.com/jtimon/til/blob/c28ab7daf/issues/open/159.org][original Til record]] remains available in its history.

Current sources are [[file:../../src/tilminal.til][src/tilminal.til]] and [[file:../../src/terminal/view.til][src/terminal/view.til]]. Tilminal
now runs a persistent PTY/ConPTY shell; its private command-runner prompt
has been removed. The older plan below predates that change. Logo placement
must be reconciled with [[./3.org][#3]]'s terminal ownership model. The logo font and
its generator are still Til assets, not files installed by Tiled's build.

*** Decision

Implement the logo prompt only in
[[file:../../src/tilminal.til][tilminal]], where we control rendering.
The terminal CLI ~til repl~ keeps its textual ~til[mode]>~ prompt
and ~til[mode]...~ continuation prompt. This issue remains open for
the tilminal implementation; this re-analysis does not implement it.

Tilminal's application and shared terminal modules moved to =jtimon/tiled=;
further terminal UI work belongs here. See [[./3.org][#3]] for the migration record.

Use Til's existing [[https://github.com/jtimon/til/blob/master/img/til_logo.ttf][img/til_logo.ttf]], generated from
[[https://github.com/jtimon/til/blob/master/img/logo-transparent.svg][img/logo-transparent.svg]] by
[[https://github.com/jtimon/til/blob/master/examples/svg2ttf.til][examples/svg2ttf.til]]. Tilminal can load it directly with
raylib's ~LoadFontEx~ and draw the logo with ~DrawTextEx~, using its
normal font for the rest of the prompt and input. The logo is mapped
to ASCII ~T~ (0x54); that mapping works when explicitly selecting the
logo font for this glyph alone. No private-use mapping, system font
registration, terminal configuration, or environment variable is
needed for this approach.

*** Re-analysis of the original terminal REPL proposal

The original goal was a single logo glyph in ordinary ~til repl~,
independent of tilminal. Several details have changed or needed
correction:

- Prompt construction is now centralized in ~src/til.til~'s
  ~repl_prompt~, shared by interactive and redirected input paths.
  The interactive editor in ~src/self/repl_editor.til~ owns redraws.
  Its ~editor_render~ measures and clips the prompt in bytes, assuming
  one byte per screen column. A UTF-8 logo would require correct
  display-width accounting and clipping without splitting its bytes,
  including narrow-terminal redraw tests.
- General Unicode string support is not a prerequisite for emitting
  one fixed glyph. Its UTF-8 bytes can be constructed using existing
  ~Str.from_byte~ calls while keeping source code ASCII-only. Waiting
  for Unicode support would not solve font selection or detection.
- The existing ~T~ mapping is unsuitable for terminal fallback:
  ordinary fonts already contain ~T~, while prioritizing our logo
  font could replace ordinary capital Ts too. A private-use codepoint
  such as ~U+E000~ would avoid replacing a normal letter, but would
  still need the terminal to select our font. Private-use assignments
  can collide with icons in other fonts.
- Font installation could be automated by ~make install~; asking
  users to install it manually is not inherently necessary. For
  example, the default Linux install could put the font under
  ~/usr/local/share/fonts/til/~ and refresh the fontconfig cache;
  Windows could register the font through its platform facilities.
  These were possibilities discussed, not approved installation
  changes for this issue.

*** Why installation checks cannot guarantee a textual fallback

An installed font and a font selected by the terminal are different
things. Some terminals discover system fallback fonts automatically;
others need explicit configuration. Another font may already supply
the private-use character, and a running terminal may need restarting
before discovering a newly installed font.

The font can also genuinely be absent when running a copied binary
or a development build. Over SSH, installing the font on the remote
machine does not install it on the client that renders the terminal.
Thus SSH is not the only complication, and installing til does not
prove the rendering terminal has selected the logo font.

Checking installation could support best-effort automatic enabling,
but there is no portable terminal query that proves our intended
glyph will be rendered. Emitting it cannot reliably detect a missing
glyph box or an unrelated icon and substitute ~til~ afterward.

An explicit opt-in such as ~TIL_FANCY_PROMPT=1~ was considered, with
terminal-specific configuration where needed (for example, kitty's
~symbol_map U+E000 TIL Logo~). This would put setup on the user,
including Windows users, and was rejected. Do not add that setting
or pursue automatic terminal selection as part of this issue.

*** Tilminal scope

This is a feature of the tilminal example, tracked generally in
[[./3.org][#3]], rather than a feature of the til language or CLI.

At the time of this original proposal, tilminal was a raylib GUI that ran shell commands through
~sh -lc~ and drew a ~$ ~ prompt. It was not a terminal emulator or a
persistent til REPL. Drawing its prompt logo was independent of adding
either capability; that decision did not require moving ~til repl~
into a GUI or implementing a tilminal-hosted REPL.

The implementation should load the existing logo asset directly,
draw the one glyph beside the normal prompt/input text, and verify
its sizing and spacing in the window. Direct rendering avoids the
terminal font-selection and fallback-detection problems above.
